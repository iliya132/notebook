# Инструкция для ИИ-агента: веб-приложение «Notebook»

## 1. Роль и ожидаемый результат

Ты — автономный senior full-stack разработчик. Создай законченное веб-приложение для личных заметок с регистрацией и входом, несколькими записными книжками, Markdown-заметками и публичными ссылками только для чтения.

Работай непосредственно в этом репозитории. Не ограничивайся макетом или набором статических страниц: результат должен запускаться локально, сохранять данные в базе, проверять права доступа на сервере и иметь автоматические тесты. Не оставляй ключевую функциональность в виде TODO, заглушек или имитации данных.

Перед началом:

1. Изучи все существующие файлы, текущий статус Git и локальные инструкции репозитория.
2. Не удаляй и не перезаписывай пользовательские изменения, не относящиеся к задаче.
3. Если репозиторий уже содержит приложение, развивай его текущий стек и стиль. Если кроме этой инструкции приложения нет, используй рекомендуемый стек ниже.
4. Выполняй работу небольшими логическими этапами и после каждого этапа запускай подходящие проверки.

## 2. Обязательный объём продукта

Пользователь должен иметь возможность:

- зарегистрироваться по имени, email и паролю;
- войти и выйти из аккаунта;
- оставаться авторизованным после перезагрузки страницы;
- видеть только свои записные книжки и заметки;
- создать, переименовать и удалить записную книжку;
- открыть записную книжку и увидеть список находящихся в ней заметок;
- создать заметку с названием и Markdown-содержимым;
- просматривать отрендеренный Markdown;
- изменять название и содержимое заметки;
- удалять заметку;
- включить доступ к конкретной заметке по непредсказуемой публичной ссылке;
- скопировать эту ссылку;
- отключить ранее выданную ссылку;
- открыть действующую публичную ссылку без авторизации и прочитать заметку;
- убедиться, что по публичной ссылке невозможно редактирование.

Все классические операции создания, чтения, изменения и удаления должны работать с реальной базой данных. Удаление должно требовать явного подтверждения в интерфейсе.

## 3. Обязательный технический стек и структура

Приложение должно состоять из независимых backend и frontend частей в одном репозитории:

```text
notebook/
├── backend/      # Java/Spring Boot REST API, Gradle Wrapper
├── frontend/     # React/TypeScript SPA
├── README.md
└── .env.example
```

### Backend

Используй:

- Java 21 LTS;
- Spring Boot на актуальной стабильной и совместимой версии;
- Gradle с обязательным Gradle Wrapper (`gradlew`, `gradlew.bat`, `gradle/wrapper/**`); предпочтителен Kotlin DSL (`build.gradle.kts`), но код приложения пиши на Java;
- Spring Web для JSON REST API;
- Spring Security для аутентификации, серверной авторизации, cookie-сессий и CSRF-защиты;
- Spring Session JDBC для серверного хранения и немедленного отзыва сессий в PostgreSQL;
- Spring Data JPA/Hibernate для доступа к данным;
- Bean Validation (`jakarta.validation`) для первичной проверки DTO;
- PostgreSQL JDBC Driver;
- Flyway для версионируемых SQL-миграций; не используй `ddl-auto=create/update` как механизм production-миграций;
- Actuator только для минимальных health/readiness endpoints без публикации секретной конфигурации;
- JUnit 5, Spring Boot Test, Testcontainers PostgreSQL и при необходимости REST Assured/MockMvc для тестов;
- springdoc/OpenAPI для документирования REST-контракта.

Архитектурно раздели контроллеры, входные/выходные DTO, прикладные сервисы, репозитории, JPA-сущности, security-конфигурацию и обработку ошибок. Не возвращай JPA-сущности напрямую из контроллеров. Все проверки владельца и транзакционные границы должны находиться на backend, а не только во frontend.

### Frontend

Используй:

- React и TypeScript в strict-режиме;
- Vite для сборки и локальной разработки;
- React Router для клиентских маршрутов;
- TanStack Query для серверного состояния, кэширования и инвалидации запросов;
- React Hook Form и Zod для форм и удобной клиентской валидации; сервер всё равно обязан повторно валидировать данные;
- Tailwind CSS или другой единообразный CSS-подход без тяжёлой UI-платформы;
- проверенный React Markdown-рендерер с GitHub Flavored Markdown и безопасной санитизацией;
- Vitest и React Testing Library для unit/component tests;
- Playwright для end-to-end сценариев;
- npm, если репозиторий не фиксирует иной JavaScript package manager.

В development настрой Vite proxy для `/api` на Spring Boot, чтобы браузер работал с относительными URL и cookie без лишнего CORS. В production frontend и API желательно публиковать под одним site/origin через reverse proxy. Если origins всё же разные, задай строгий allowlist CORS, включи credentials и корректно настрой `SameSite`/`Secure`; wildcard origin с credentials запрещён.

Не привязывай бизнес-логику к React-компонентам. Клиент отвечает за интерфейс и вызов API, но никогда не считается доверенной границей безопасности.

## 4. Модель данных

Спроектируй миграции как минимум для следующих сущностей. Названия полей могут соответствовать соглашениям выбранного ORM, но смысл и ограничения должны сохраниться.

### User

- `id`: UUID или другой устойчивый уникальный идентификатор;
- `name`: непустое отображаемое имя;
- `email`: нормализованный email, уникальный без учёта регистра;
- `passwordHash`: только стойкий хеш пароля, никогда не исходный пароль;
- `createdAt`, `updatedAt`.

### Session

- идентификатор сессии или хеш непрозрачного токена;
- `userId`;
- срок действия;
- дата создания;
- при необходимости метаданные для отзыва сессии.

Если выбранная библиотека авторизации использует другую стандартную сессионную схему, следуй её безопасной схеме.

### Notebook

- `id`;
- `ownerId` со ссылкой на `User`;
- `title`, обязательное и ограниченное по длине;
- `createdAt`, `updatedAt`;
- индекс по `ownerId` и времени обновления.

### Note

- `id`;
- `notebookId` со ссылкой на `Notebook`;
- `title`, обязательное и ограниченное по длине;
- `content`, строка с Markdown, может быть пустой;
- `createdAt`, `updatedAt`;
- индекс по `notebookId` и времени обновления.

### NoteShare

- `id`;
- `noteId`, уникальная ссылка на `Note`;
- `tokenHash`, уникальный хеш публичного токена;
- `createdAt`;
- опционально `expiresAt`, только если срок действия реализован полноценно;
- опционально `revokedAt`; альтернативно при отключении доступа запись можно удалить.

Публичный токен должен генерироваться криптографически стойким генератором и содержать не менее 256 бит случайности. В базе сохраняй хеш токена, а не сам токен. Исходный токен допустимо показать владельцу при создании ссылки; если приложение должно повторно показывать ту же ссылку, можно хранить защищённый непрозрачный идентификатор при условии документированного решения. Более простой безопасный вариант — при повторном включении создавать новую ссылку.

Определи поведение каскадного удаления явно:

- удаление пользователя удаляет его сессии, записные книжки, заметки и публичные ссылки;
- удаление записной книжки удаляет её заметки и ссылки на них;
- удаление заметки немедленно делает публичную ссылку недействительной.

## 5. Авторизация и безопасность

Различай аутентификацию и авторизацию:

- аутентификация устанавливает личность пользователя;
- авторизация проверяет, имеет ли он право работать с конкретной записной книжкой или заметкой.

Обязательные правила:

1. Хешируй пароли Argon2id или bcrypt с безопасными параметрами. Никогда не записывай пароль, хеш пароля, сессионный или публичный токен в логи.
2. Сессионная cookie должна иметь `HttpOnly`, `SameSite=Lax` или более строгое значение, `Secure` в production и разумный срок действия.
3. После выхода сессия должна быть отозвана на сервере, а cookie очищена.
4. Защити изменяющие запросы стандартным механизмом Spring Security CSRF. Для React SPA выдай отдельный CSRF-токен безопасным способом и отправляй его в заголовке каждого изменяющего запроса; CSRF-токен не заменяет cookie-сессию. Не отключай CSRF глобально и не полагайся только на скрытие кнопок.
5. На каждом серверном чтении и изменении приватных данных проверяй владельца. Никогда не загружай объект по одному `id`, а затем без проверки не возвращай и не изменяй его.
6. Для заметки проверяй цепочку `note -> notebook -> owner`; перед переносом заметки также проверяй целевую книжку.
7. Возвращай нейтральные ошибки для входа и регистрации, не раскрывая существование аккаунта сверх необходимого.
8. Добавь ограничение частоты попыток для входа, регистрации и разрешения публичных ссылок либо чётко подготовь абстракцию и документируй production-механизм, если локальная реализация зависит от инфраструктуры.
9. Валидируй все входные данные на сервере, даже если UI уже выполняет проверку.
10. Ограничь разумный размер названий и Markdown-содержимого. Например: имя 1–100, название книжки и заметки 1–200, содержимое заметки до 1 МБ.
11. Markdown считается недоверенным вводом. Запрети или безопасно санитизируй raw HTML, опасные URL-схемы, скрипты и обработчики событий. Проверь защиту от stored XSS.
12. Не возвращай внутренние трассировки и секреты пользователю. Конфиденциальные значения бери только из переменных окружения.

Критически важно: знание UUID записной книжки или заметки не даёт доступа к ней. Запрос одного пользователя к объектам другого должен завершаться `404` или `403` и ничего не изменять.

## 6. Контракт серверной части

Реализуй версионированный JSON REST API Spring Boot под префиксом `/api/v1`. Контроллеры принимают и возвращают DTO, используют единый формат ошибок и не раскрывают внутренние исключения.

### Аутентификация

- `POST /api/v1/auth/register` — регистрация пользователя;
- `POST /api/v1/auth/login` — вход по email и паролю и создание cookie-сессии;
- `GET /api/v1/auth/me` — получение текущего пользователя;
- `POST /api/v1/auth/logout` — выход, отзыв сессии и очистка cookie.

### Записные книжки

- `GET /api/v1/notebooks` — список книжек текущего пользователя;
- `POST /api/v1/notebooks` — создание книжки;
- `GET /api/v1/notebooks/{notebookId}` — книжка и список её заметок;
- `PATCH /api/v1/notebooks/{notebookId}` — переименование книжки;
- `DELETE /api/v1/notebooks/{notebookId}` — удаление книжки.

### Заметки

- `POST /api/v1/notebooks/{notebookId}/notes` — создание заметки в книжке;
- `GET /api/v1/notes/{noteId}` — получение заметки владельцем;
- `PUT /api/v1/notes/{noteId}` — изменение названия и Markdown-содержимого;
- `DELETE /api/v1/notes/{noteId}` — удаление заметки.

### Публичный доступ

- `POST /api/v1/notes/{noteId}/share` — создание или ротация публичной ссылки владельцем;
- `GET /api/v1/notes/{noteId}/share` — статус публичного доступа владельцу без утечки хеша токена;
- `DELETE /api/v1/notes/{noteId}/share` — отключение ссылки владельцем;
- `GET /api/v1/public/notes/{token}` — анонимное чтение заметки по токену.

Для изменяющих операций возвращай структурированные ошибки валидации. Используй подходящие коды HTTP: `201` для создания, `204` для успешного удаления, `400/422` для некорректных данных, `401` без сессии, `403/404` при отсутствии доступа, `409` для конфликта уникальности или версии. Реализуй единый `@RestControllerAdvice` с машиночитаемым `code`, человекочитаемым `message`, опциональными ошибками полей, `timestamp` и request/trace ID. Не раскрывай в публичном ответе хеш ссылки, stack trace или приватные данные владельца.

Избегай потерянных обновлений: добавь JPA-поле `@Version` и передавай версию в DTO обновления либо реализуй эквивалентный условный запрос. При устаревшей версии отвечай `409 Conflict`; повторный медленный запрос не должен молча затирать более новое изменение.

## 7. Маршруты и пользовательский интерфейс

Предусмотри как минимум следующие страницы:

- `/register` — регистрация;
- `/login` — вход;
- `/app` — список записных книжек пользователя;
- `/app/notebooks/[notebookId]` — выбранная книжка и её заметки;
- `/app/notes/[noteId]` — редактор заметки и предпросмотр;
- `/share/[token]` — публичное чтение заметки без элементов редактирования.

Требования к интерфейсу:

- адаптивная вёрстка для телефона и компьютера;
- понятная навигация между книжками и заметками;
- состояния загрузки, пустого списка и ошибки;
- формы с доступными label, сообщениями валидации и управлением с клавиатуры;
- видимый индикатор несохранённых изменений и состояния сохранения;
- сохранение по явной кнопке; автосохранение допустимо дополнительно, если оно надёжно и покрыто тестами;
- Markdown-редактор с режимами «Редактирование» и «Предпросмотр» или разделённой панелью;
- меню заметки с действиями «Поделиться», «Копировать ссылку», «Отключить ссылку», «Удалить»;
- подтверждение удаления заметки и книжки с ясным описанием последствий;
- публичная страница показывает только название, безопасно отрендеренный Markdown и нейтральное обозначение режима чтения;
- не показывай email владельца и элементы приватной навигации на публичной странице;
- недействительная, отозванная или удалённая ссылка отображает аккуратную страницу `404`.

Маршруты `/app/**` защищай на сервере. Перенаправление неавторизованного пользователя на `/login` полезно для UX, но не заменяет проверку в каждой операции с данными.

## 8. Поведение и пограничные случаи

Реализуй и проверь следующие сценарии:

- email при регистрации нормализуется: пробелы удаляются по краям, регистр не создаёт второй аккаунт;
- пустые и состоящие из пробелов названия отклоняются;
- заметка может иметь пустое содержимое, но не пустое название;
- после удаления текущей заметки пользователь возвращается в её книжку;
- после удаления книжки пользователь возвращается к списку книжек;
- удаление непустой книжки требует явного подтверждения и удаляет вложенные заметки транзакционно/каскадно;
- две заметки и две книжки могут иметь одинаковые названия;
- публичная ссылка работает в окне без активной сессии;
- после отключения публичная ссылка перестаёт работать немедленно;
- повторное включение общего доступа создаёт новый токен, старый не оживает;
- изменение приватной заметки сразу отражается при чтении по действующей ссылке;
- публичная ссылка не даёт методов, форм или API-возможности изменить заметку;
- пользователь A не может читать, менять, удалять или публиковать объекты пользователя B даже при ручной подстановке ID;
- одновременное редактирование не приводит к незаметной потере более свежих данных;
- вредоносный Markdown вроде `<script>` или `javascript:` не исполняется.

## 9. Тестирование

Создай тесты, которые доказывают не только happy path, но и разграничение доступа.

### Модульные тесты

- схемы валидации;
- нормализация email;
- генерация и хеширование публичного токена;
- безопасная конфигурация Markdown;
- функции проверки владельца, если они вынесены отдельно.

### Интеграционные тесты

- регистрация, вход, неверный пароль и выход;
- CRUD записной книжки;
- CRUD заметки;
- каскадное удаление;
- публичная ссылка: создание, анонимное чтение, отзыв;
- невозможность доступа пользователя A к данным пользователя B;
- отклонение некорректных входных данных;
- конфликт версии при одновременном сохранении.

### End-to-end тесты

Минимум один полный сценарий:

1. Новый пользователь регистрируется.
2. Создаёт книжку и заметку.
3. Вводит Markdown и видит безопасный предпросмотр.
4. Сохраняет и обновляет страницу без потери данных.
5. Включает общий доступ и копирует ссылку.
6. Открывает ссылку в отдельном неавторизованном контексте и видит только чтение.
7. Отключает ссылку и получает `404` при повторном открытии.

Отдельный e2e или интеграционный сценарий должен проверять изоляцию двух пользователей.

Тесты должны использовать отдельную тестовую базу данных. Не допускай очистку development/production базы тестовым раннером.

## 10. Конфигурация и локальный запуск

Добавь:

- `.env.example` без реальных секретов;
- `.gitignore`, исключающий `.env*` с разумным исключением для `.env.example`, сборочные файлы, зависимости и отчёты тестов;
- Flyway-миграции базы данных в `backend/src/main/resources/db/migration`;
- при необходимости `docker-compose.yml` только для локального PostgreSQL;
- Gradle-задачи для сборки, форматирования/статического анализа и backend-тестов;
- frontend-скрипты `dev`, `build`, `lint`, `typecheck`, `test` и `test:e2e`;
- удобную корневую команду или чёткую инструкцию для одновременного локального запуска backend и frontend;
- seed-скрипт только если он действительно помогает разработке; тестовые пароли не должны использоваться в production;
- подробный `README.md` с требованиями, настройкой окружения, запуском БД, миграциями, тестами и описанием архитектурных решений.

### Подключение к PostgreSQL в Yandex Cloud

Целевая база использует два PostgreSQL-хоста, порт `6432`, обязательную проверку TLS-сертификата и подключение к доступному read-write узлу:

- user: `iliya132`;

Пароль базы данных является секретом. Не записывай его в Git, исходный код, `application.yml`, Docker image, тестовые fixtures, логи или документацию. Получай его из `DB_PASSWORD` через секреты окружения/платформы. Если пароль был передан открытым текстом в постановке задачи или переписке, считай его скомпрометированным и потребуй его ротацию перед production-запуском.

### Yandex Lockbox

Для production используй существующий секрет Yandex Lockbox:

- secret ID: `e6q18smvei2glc3po3vt`;
- console: `https://console.yandex.cloud/folders/b1gld75v3ghk0529ib1t/lockbox/secret/e6q18smvei2glc3po3vt/overview`;
- ожидаемое назначение payload entry: пароль пользователя PostgreSQL `iliya132`;
- имя payload key не угадывай: прочитай метаданные/настройку секрета и зафиксируй фактический key в deployment-конфигурации.

Предпочтительный механизм зависит от среды запуска:

1. Для Yandex Serverless Containers передавай конкретный payload entry непосредственно в environment variable `DB_PASSWORD` средствами платформы.
2. Для Yandex Managed Service for Kubernetes используй External Secrets Operator и workload identity/service account, не статический IAM-ключ в Kubernetes Secret manifest.
3. Для VM или другой среды Yandex Cloud используй привязанный к workload сервисный аккаунт и IAM-токен из metadata service для чтения текущего payload через Lockbox API. Не создавай долгоживущий ключ сервисного аккаунта без необходимости.
4. Для локальной разработки разрешено вручную задать `DB_PASSWORD` в игнорируемом Git файле окружения или shell-сессии. Локальные тесты должны использовать отдельный пароль Testcontainers и не обращаться к Lockbox.

Выдай runtime-сервисному аккаунту только роль `lockbox.payloadViewer` на конкретный секрет, а не на весь каталог. Если секрет зашифрован пользовательским KMS-ключом, дополнительно нужна роль `kms.keys.encrypterDecrypter` на этот ключ. Приложению не нужны права редактирования, создания или удаления секретов.

Не логируй ответ Lockbox API и не помещай payload в exception message, Actuator `/env`, tracing tags или metrics labels. Получай текущую активную версию, чтобы ротация не требовала изменения исходного кода; после ротации перезапускай workload или используй поддерживаемое платформой обновление секрета. При отсутствии секрета, нужного payload key или доступа заверши запуск с безопасной диагностикой без значения секрета.

Официальные ссылки:

- [получение payload через Lockbox API](https://yandex.cloud/en/docs/lockbox/api-ref/Payload/get);
- [права доступа Yandex Lockbox](https://yandex.cloud/en/docs/lockbox/security/);
- [передача Lockbox-секрета в Serverless Container](https://yandex.cloud/en/docs/serverless-containers/operations/lockbox-secret-transmit);
- [интеграции Lockbox с сервисами Yandex Cloud](https://yandex.cloud/en/docs/lockbox/concepts/services).

Безопасный пример `.env.example`:

```dotenv
SPRING_DATASOURCE_URL=jdbc:postgresql://rc1b-gqjk98jh57e1ethn.mdb.yandexcloud.net:6432,rc1d-2qgn0ma849438o7q.mdb.yandexcloud.net:6432/iliya132-db?targetServerType=primary&sslmode=verify-full&sslrootcert=/absolute/path/to/root.crt
SPRING_DATASOURCE_USERNAME=iliya132

LOCKBOX_SECRET_KEY=replace-with-existing-payload-key

```

В `application.yml` используй `spring.datasource.password: ${DB_PASSWORD}` и обязательную подстановку остальных production-настроек из окружения. Для локальной БД разрешён отдельный профиль `local`; для интеграционных тестов используй Testcontainers, а не облачную БД.

Загрузи официальный корневой сертификат Yandex Cloud по документированному каналу, проверь его происхождение и смонтируй/укажи абсолютный путь через конфигурацию окружения. Не отключай проверку сертификата (`sslmode=require` не является заменой `verify-full`). Учитывай, что JDBC URL с `&` нужно корректно заключать в кавычки в shell/CI.

Приложение должно завершать запуск с понятной ошибкой при отсутствии обязательной конфигурации. Не коммить `.env`, дампы базы, реальные ключи, пароли, токены, cookies или приватные сертификаты.

## 11. Качество реализации

- Backend должен собираться на Java 21 через Gradle Wrapper; зафиксируй Java toolchain и совместимые версии зависимостей.
- Включи Checkstyle/Spotless и статический анализ Java-кода либо эквивалентные проверки, не отключая ошибки без обоснования.
- TypeScript frontend должен быть в strict-режиме; не используй `any` без локального обоснования.
- Не дублируй проверки владельца в десятках мест: создай небольшие переиспользуемые функции/репозитории с безопасными запросами.
- Операции, меняющие несколько связанных записей, выполняй в сервисах с корректными `@Transactional` границами.
- Все даты храни в UTC; форматируй их на уровне интерфейса.
- Добавь индексы для наиболее частых запросов.
- Не делай premature optimization, но избегай N+1 JPA-запросов на основных страницах.
- Не используй `dangerouslySetInnerHTML` с неочищенным вводом.
- Не прячь критические ошибки Gradle, линтера и TypeScript настройками.
- Компоненты интерфейса должны иметь ясные названия и ограниченную ответственность.
- Логи должны помогать диагностике, но не содержать секретов и приватного Markdown-содержимого.

## 13. Критерии готовности

Работа считается завершённой только если одновременно выполнено следующее:

- приложение устанавливается и запускается по инструкции на чистом окружении;
- миграции успешно создают схему с нуля;
- регистрация, вход, выход и восстановление сессии работают;
- CRUD книжек и заметок сохраняет данные в PostgreSQL;
- разграничение данных двух пользователей проверено автоматическими тестами;
- Markdown корректно отображается и не допускает выполнения вредоносного HTML/JavaScript;
- публичная ссылка доступна без входа, даёт только чтение и может быть отозвана;
- секрет публичной ссылки невозможно получить из обычного ответа API или напрямую из БД в открытом виде;
- основные формы доступны с клавиатуры и корректно работают на мобильной ширине;
- Gradle check, frontend lint/typecheck, unit/integration tests, e2e tests и production-сборки обеих частей завершаются успешно;
- в репозитории нет секретов, временных файлов, дампов БД и случайно закоммиченных зависимостей;
- README точно описывает реальный способ запуска и тестирования.
